# 2026-09-23 — Claude Opus 5.5 on the anthropic path, read back

The owner asked to move to Opus 5.5. `claude-opus-5-5` postdates this
coordinator's training data and is absent from the harness's `/model`
list — `/model opus5.5` and `/model opus[5.5]` are both refused — so the
first question was whether the id serves at all through the launcher.
It does. The second question was not asked and is the one that matters:
its default effort is not Opus 5's.

## Resolution

`bin/fabric-model set --provider anthropic code-high claude-opus-5-5` on
this agent's local layer, then `runtime/openrouter/launch --print
--provider anthropic`:

```
session     : claude-opus-5-5  (the code-high class)
code-low    : claude-haiku-4-5-20251001
code-medium : claude-sonnet-5
code-high   : claude-opus-5-5          (from local)
code-plan   : claude-fable-5-1
code-review : claude-opus-5[1m]        (pinned in the agent file)

export ANTHROPIC_DEFAULT_OPUS_MODEL=claude-opus-5-5
export AGENT_FABRIC_LAUNCH_SESSION_MODEL=claude-opus-5-5
```

The review class did not move, as designed: it is gated by
`routing/policies/review-grade.json`, whose closed set does not admit a
5.5 id. Nothing in `tools/fabric/routing.py` validates a model id
against a catalogue, so the profile layers accept any string — the
adapter's shape check is all that stands between a typo and a launch.

## Served

`launch --provider anthropic --output-format json -p …`, session
`16ff4ce2`: `init model: claude-opus-5-5`, `is_error: false`, the
answer written unprompted and naming the model, `modelUsage` carrying
one key, `claude-opus-5-5`; `total_cost_usd` 0.186.

**Control.** The same probe with `code-high` set to
`claude-opus-9-9-not-a-model`: `is_error: true`, `modelUsage: []`,
result "There's an issue with the selected model", and the harness
logged `[claude-code:unrecognized_model]`. So the pass above is the
model answering, not a silent fallback to the exported default.

## Effort: the fabric has no opinion, and that now costs a level

`output_config.effort` is an API parameter (`low`…`max`); Claude Code
2.1.280 exposes it as `claude --effort <level>`, and exports
`CLAUDE_EFFORT` into the tool environment as a readout of the running
session — it is set by no `settings.json` env block, no shell profile,
and nowhere in this repository.

Measured, same launcher, same profile, one variable changed:

```
this session, claude-opus-5     CLAUDE_EFFORT=high
launched,     claude-opus-5-5   EFFORT=medium
```

Opus 5 defaults to `high`; Opus 5.5 defaults to `medium`. The fabric
sets effort nowhere, so every model it has pinned so far happened to
default to `high` and the question never arose. Opus 5.5 is the first
that does not: moving `code-high` to it drops every session a level of
thinking, with no commit, nothing to review, and a symptom that reads
as a worse model rather than a changed default.

What this decides: **the model id alone is not the routing decision.**
Effort belongs with it — resolved per class, exported by the launcher,
and visible in `--print` and `bin/fabric-status` — or a vendor's default
change silently re-tunes the fleet. The alternative considered and not
taken is pinning `--effort high` on the launcher: it fixes this bump and
leaves the next one to be found the same way.

## What is not established here

- Whether `claude-opus-5-5` should be admitted to the review grade, and
  whether the `[1m]` marker means anything for a model whose context is
  natively 1M.
- The other breaking changes of 5.5 are read from documentation, not
  measured: thinking cannot be disabled, forced `tool_choice` `any`/`tool`
  returns 400, computer use requires `computer_toolset_20260801`.
  Nothing in this repository uses the first two today.
